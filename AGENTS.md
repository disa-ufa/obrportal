# OBRPORTAL — правила разработки

## Цель
Развивать работоспособную систему обучения.
Приоритет — завершённые пользовательские функции.

## Перед изменениями
- Прочитать существующую реализацию.
- Установить причину проблемы.
- Проверить текущую ветку и изменения Git.
- Не создавать копии проекта без необходимости.
- Не создавать новый сервис, если нужный уже существует.

## Реализация
- Одна задача — один ограниченный набор изменений.
- Не отключать проверки безопасности ради результата.
- Не придумывать данные пользователей и документов.
- Сохранять существующие API-контракты.
- После двух неудачных исправлений пересмотреть подход.

## Проверки
- Выполнить целевые автоматические тесты.
- Проверить сборку затронутого приложения.
- Проверить пользовательский сценарий.
- Полную регрессию проводить перед релизом.
- Не считать успешную сборку доказательством готовности.

## Данные и production
- Не удалять реальные учебные данные.
- Не менять production без отдельного разрешения.
- Не выполнять миграции без проверки и согласования.
- Не отключать RBAC и аудит.
- Не изменять исторические утверждения и выгрузки
  без предусмотренной процедуры.
- Не выполнять docker compose down -v.
- Не помещать секреты и персональные данные в Git.

## Завершение задачи
Сообщить:
1. Что изменено.
2. Что проверено.
3. Что работает для пользователя.
4. Какие ограничения остались.

Основная ветка GitHub — main.
Разработка — в отдельных ветках через Pull Request.
Объединение в main не означает deployment.
