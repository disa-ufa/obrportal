# M4.R6.13D.7 — предотвращение тупиков применимости и ручных правок реестров

Статус: **staged / review required**. База для этой ветки — PR #205,
`feature/learner-completion-profile-gate-20261117`, коммит
`df5b0c2c865a0318ac04ca2ef655828a6bc6bf19`.
Это не инструктаж для выполнения операций на действующей базе.

## Подтверждённые проблемы

1. В M4P9 находилось утверждённое обязательство Минтруда без сохранённого
   решения применимости. Общий writer намеренно блокирует модификацию
   утверждённых исторических записей; повторное утверждение не является
   исправлением. Локально проведена адресная сверка отдельным проверенным
   сервисом с одним атомарным COMMIT и read-only postcheck. **Нельзя**
   выполнять эту операцию повторно на том же обязательстве.
2. Другая запись уже входила в существующую XML-партию. Повторное включение
   должно оставаться заблокированным независимо от актуальности правила.
3. Форма редактирования профиля скрывала конкретный HTTP 409 за общей фразой.
   Backend проверяет уникальность СНИЛС на уровне модели/SQL, но при
   `IntegrityError` с изменением СНИЛС может возвращать то же сообщение и
   для другого конфликта. Не выводить PII чужого профиля в ответе/логах.
4. Backend и frontend M4 не входят в основной `main`: широкие изменения
   находятся в черновом PR #205 и требуют отдельного merge/deploy review.
   Другой черновой PR #204 посвящён юридически иной операции —
   восстановлению исторического утверждения и не заменяет сверку
   отсутствующей применимости.

## Обязательные инварианты

- Всякая **новая** операция утверждения для передачи в Минтруд проверяет
  существование актуального решения `required` с текущими
  `rule_code`, `rule_version`, `input_fingerprint`.
  Для `not_required` и `needs_review` требуется отдельная явная
  ветвь, нельзя молча считать их `required`.
- Проверка применимости, готовности, полномочий, уникальности события
  утверждения и истории экспорта должна происходить внутри согласованной
  транзакции с существующим порядком блокировок C → S → D → O.
  Проверка до транзакции — только подсказка в UI, не разрешение на экспорт.
- Сохранение применимости и её события атомарно. Существующее утверждение,
  протокол, прогресс обучения, документы и XML-батчи не переписываются
  вспомогательной сверкой.
- Историческая сверка: отдельный авторизованный маршрут; `apply=False`
  по умолчанию, операторское основание, явное подтверждение,
  актуальные fingerprint/event ID и уникальный `operation_id`.
  Контракт восстановления должен быть устойчив к повторным запросам
  и неизвестному исходу COMMIT: сначала запрос статуса, потом решение,
  но никогда слепой повтор.
- Любая запись с историей batch-item, попыткой отправки или уже
  выгруженным approval event должна оставаться недоступной для повторного
  экспорта без самостоятельного правового основания и нового решения.
- При изменении значимых полей профиля пересчитать готовность и
  инвалидировать относящиеся к нему утверждения, сохранив историю.
  Не объединять личности и не переназначать СНИЛС автоматически.

## План внедрения после безопасного UX-пакета

### P0. Read-only инвентаризация

Снять **только в локальной изолированной базе** сводку всех обязательств:
регистрация/курс, status, decision state, fingerprint, approval-current,
batch/attempt history, data readiness, immutable event history.
Чётко разделить категории:
`missing_approved_no_history`, `stale_approval`,
`already_exported`, `manual_or_legacy_decision`,
`current_ready`, `data_not_ready`, `history_conflict`.
Не выгружать ФИО, СНИЛС и пароли в общий CI и репозиторий.

### P0. Prevention для будущих утверждений

В отдельном изменении адаптировать административный Mintrud approval path:
`load_current_registry_applicability_inputs` + persist/validate existing
decision в той же согласованной транзакции. До правки получить
контрактные тесты по `approved`, `ready`, `needs_approval`,
`required`/`not_required`/`needs_review`, stale/legacy/manual,
гонкам с писателями источников, сохранению законной повторной
аттестации. Не переносить writer в обычный маршрут `approved`.

### P1. Recovery для legacy

Отдельная таблица/страница для индивидуальных кандидатов,
предпросмотр, отказ с точной машинной причиной, подтверждение.
Использовать существующий dry-run сервис и review-проверку,
выработанную M4.R6.13D.5C–5D; запретить массовый blind backfill.
Операция применима только к уже утверждённой записи без истории XML
и без старых событий применимости. Без запуска на старых данных
до отдельного допуска.

### P1. Операторы и профиль

Показать локализованные ошибки 401/403/409/422; не раскрывать
СНИЛС другого пользователя. Предупреждать о влиянии изменений на
утверждения, показывать итог после обновления и объяснять
невозможность повторного включения в XML.

### P2. QA / release gate

- Postgres реальные транзакции: PASS / ROLLBACK / rejected duplicate /
  concurrent approval and export / interleaved profile update / timeout
  and unknown COMMIT outcome.
- FastAPI: actual authentication, RBAC, CSRF (если предусмотрен),
  account/org scope, statuses 401/403/404/409/422; no actor spoofing.
- Frontend: блокировка по всем блокирующим причинам и обязательное
  обновление из API; не принимать cached approval как экспортное разрешение.
- Снимки пользователей, enrolments, courses, progress, results, documents,
  3 существующих XML-партий и аудита должны совпасть при postcheck,
  кроме адресно разрешённых строк.
- Проверенные резервные копии PostgreSQL, MinIO и private-documents,
  совместимость Alembic, CI и независимая restore-проба до любого
  production deployment.

## Область этого PR

Неразрушающие UX-улучшения, тесты и локальная read-only утилита
\`python -B -m app.mintrud_missing_applicability_inventory\`.
Утилита проверяет точную локальную идентичность M4P9 и выводит
только агрегаты: approved without decision, наличие batch items,
attempts, immutable applicability events и preliminary no-history.
Она **не** проверяет индивидуальную актуальность утверждений и **не**
разрешает автоматическую сверку.
**Не реализует и не разрешает автоматически** ни новые утверждения,
ни восстановление исторической применимости, ни изменение XML,
ни миграции, ни production deployment. Эти задачи требуют отдельного
review/CI и отдельного решения о внедрении.
