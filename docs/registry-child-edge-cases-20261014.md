## Доказательство конкурентности и сохранности данных

Конкурентные проверки используют реальные SQLAlchemy/asyncpg-транзакции,
настоящие source/decision/row locks и неизменённый resolver. Ожидание
подтверждается **точной парой PID через `pg_blocking_pids`**, дополнительно
проверяется `pg_stat_activity.wait_event_type = 'Lock'`. Событие запуска задачи
не считается доказательством блокировки. Короткий sleep применяется только
между опросами реального графа PostgreSQL, а не вместо проверки блокировки.

В порядке «писатель первым» изменение выполняется только после подтверждения
блокировки читателя, затем commit требует отказа читателя, rollback позволяет
продолжить с прежним scope. В обратном порядке писатель реально ждёт читателя;
повторное чтение под удерживаемыми блокировками даёт тот же scope.

Каждая гонка создаёт непустую синтетическую историю двух назначений и обоих
реестров: четыре решения, события, обязательства, попытки, пакета и элемента
пакета. До/после сравниваются все колонки решений, событий, попыток, пакетов и
элементов, включая UUID, версии, JSON, timestamps и количество строк.
У обязательств сравниваются все поля, кроме явно изменяемой `document_id`
и служебной `updated_at`; ссылки проверяются отдельно. Rollback сравнивает
полную исходную строку документа/контекста.

В читателе сохраняется ORM-объект, загруженный до ожидания: свежие скалярные
проекции resolver должны выявить изменение даже при наличии старого объекта
в identity map.

## Ограничения и приёмка

- Протокол остаётся не подключённым к рабочим писателям. Тестовые писатели
  явно соблюдают общий порядок блокировок; прохождение тестов не доказывает
  безопасность legacy endpoint, который этот порядок обходит.
- Два существующих legacy XFAIL про attempt после решения применимости
  относятся к незавершённой интеграции, а не к этим изменениям resolver.
- Проверка относится к связям и сохранности истории, а не к атомарности
  внешних файлов/отправок с транзакцией БД.
- На этапе локальной проверки GitHub CI не запускался: действовал запрет push.
  Commit и обычный push в существующую ветку PR #191 затем разрешены отдельно;
  статус CI проверяется для нового SHA после публикации.
- Main, production, Stage17B, существующие контейнеры и базы не изменялись;
  merge и deployment не выполнялись. M2.1.4 не начинался.

Перед очисткой проверено отсутствие оставшихся `test_*` БД. Созданные для
этого задания четыре контейнера и внутренняя сеть удалены; существующие
контейнеры остались запущены с прежними ID.

Итог: **M2.1.3 готов к приёмке в пределах dormant resolver и его тестов**.
Новых дефектов, падений или xfail нет. Это не приёмка M2.1 целиком и не
разрешение на интеграцию с production. Переход к M2.1.4 не выполнялся.
